# Caching and fast-load plan (2026-11-24)

Read-only analysis of `client/` (Vite 7, React 19, supabase-js 2, Vercel). No code was changed. Tasks are sized for Sonnet.
Tasks marked **[LIVE VOTING]** touch vote or ballot-window logic and need Rickey's review.

## 0. What exists today (facts from the code)

- No service worker, no manifest, no PWA plugin. `client/vercel.json` is only the SPA rewrite (`/(.*)` -> `/index.html`), no `headers`. Vercel's default for hashed `/assets/*` is already immutable; `index.html` and `/fonts/*`, `/sidechatters/*`, `/blank-pfp.png` get Vercel defaults (revalidate, no long TTL).
- `client/public/sidechatters/` is 15 MB of full-size JPGs (one is 2 MB), loaded by `FallingProfileBallPhysics` and the landing page. The biggest single payload in the app. Fonts are 468 KB (two woff2 preloaded; bold is a TTF, not preloaded).
- Data layer: every `api/*` function calls Supabase directly, no cache, no dedup, no abstraction. No React Query/SWR. Only local persistence: submission confirmation (`jsc.submitted.v1.<ballot>.<user>`), reveal-seen flag, profile-setup-skipped flag, home prefs.
- `AppShell` / `HomePage` / `UserDataProvider` each fetch profile separately: `UserContenxt` loads `profiles *` + `members` (all columns, `.single()`); `HomePage` loads `profiles.image_url` again just for the setup check.
- `ui/useHomeData` -> `loadHomeData`: `fetchCurrentSeason` + `fetchBallotSummaries` (3 follow-up queries + `auth.getUser()` network call), then results (`fetchBallotDetail` per ballot: ballot + categories+nominees, plus round_nominees for rounds), committee: release status (re-fetches all ballot details again), `fetchAllVotes` (paged) + `fetchMembers`. Then `pages/home/useHomeData` adds `fetchMembers` + `fetchMemberAvatars` (which itself calls `fetchMembers` again) once released. So `members` is fetched up to 3 times per Home load; ballot detail up to 2x per ballot.
- `supabase.auth.getUser()` is a network call in `fetchMyVotes`, `castVote`, `clearVote`, `fetchBallotSummaries`. It adds a round trip to every vote save and breaks offline. `getSession()` is local.
- VotePage: loads detail + my votes in parallel, shows plain "Loading..." text (no skeleton). Has a per-category save queue (`chains`, `seqs`, `confirmed`) that is in-memory only, with rollback to `confirmed` on failure and a manual "Try again". Nothing survives reload or tab close. Votes are `upsert ... onConflict ballot_id,category_id,voter_id`, so replays are idempotent per (ballot, category, voter): the last write wins, no duplicate rows possible.
- Avatars: public bucket `profile-pics`, `getPublicUrl` stored whole in `profiles.image_url`. Upload path is `<name>-<Date.now()>` so every URL is unique and effectively immutable. Upload does not pass `cacheControl` (Supabase default 3600 s), no client resize (raw phone photo, multi-MB), no transform params when rendering. `Avatar` renders `<img>` with an initials fallback on error, but no width/height attrs (circle size is fixed by CSS so no layout shift for avatars specifically).
- `Skeleton`/`SkeletonScreen` exist in `ui/`. Check which screens use them before adding.
- Home refetch: `useHomeData` reloads when the tab is visible after >60 s; `useRefetchOnFocus` (30 s throttle) in VotePage refreshes ballot detail.
- The memory note (`supabase-offline-cache.md`): "free-tier DB pauses; later cache per-user info so users can use the app while Supabase is asleep." Marked not v1; "keep v1 fetching easy to cache." This plan is that follow-up. Important caveat: when the project is paused, **Auth also fails** (token refresh), so a cached read view must tolerate an unrefreshable session (see 4.4).

## 2. (a) Static assets and PWA

- Use `vite-plugin-pwa` (Workbox `generateSW`) with `registerType: "prompt"`, not autoUpdate. A silent skipWaiting mid-vote could swap JS under a user who is saving a vote; prompt shows a toast "Update available, Reload" and only reloads when the user taps (or on next cold start).
- Precache: app shell (`index.html`, hashed js/css), the 3 fonts, `blank-pfp.png`, icons. Exclude `sidechatters/**` and any `*.jpg` over 100 KB from precache (`globIgnores`).
- `navigateFallback: "/index.html"` with `navigateFallbackDenylist` for `/api`, anything with a file extension, and Supabase auth callback routes (`/confirmed`, `/reset-password` query fragments contain tokens in the URL hash; the SW must not interfere: hash is never sent to server, so fallback is fine, but verify manually).
- Runtime caching rules (Workbox `runtimeCaching`):
  - Supabase Storage public avatars: `CacheFirst`, `cacheableResponse: {statuses:[200]}`, `expiration: {maxEntries: 100, maxAgeSeconds: 30d}`.
  - `/sidechatters/*`: `CacheFirst`, 60 d, 20 entries.
  - **Supabase REST/Auth/RPC (`*.supabase.co/rest|auth|rpc/*`): `NetworkOnly`, explicitly.** Data caching is done in app code (section 3) where we control keys, per-user scoping, and the sign-out wipe. An SW cache of REST GETs is keyed by URL only and would leak one user's rows to the next user on a shared device and ignore the Authorization header.
- Manifest: name "JSC Oscars", `display: standalone`, `theme_color #18181B`, `background_color #18181B`, 192/512 + maskable icons. Needed for install and iOS home-screen use. Keep `viewport-fit=cover` (already set).
- `vercel.json` headers (keep the rewrite; rewrites do not apply to real files):
  ```
  headers: [
   { source: "/assets/(.*)",   headers: [{ key: "Cache-Control", value: "public, max-age=31536000, immutable" }] },
   { source: "/fonts/(.*)",    headers: [{ key: "Cache-Control", value: "public, max-age=31536000, immutable" }] },
   { source: "/sidechatters/(.*)", headers: [{ key: "Cache-Control", value: "public, max-age=2592000, stale-while-revalidate=86400" }] },
   { source: "/(index.html)?", headers: [{ key: "Cache-Control", value: "no-cache" }] },
   { source: "/sw.js",         headers: [{ key: "Cache-Control", value: "no-cache" }, { key: "Service-Worker-Allowed", value: "/" }] },
   { source: "/manifest.webmanifest", headers: [{ key: "Cache-Control", value: "no-cache" }] }
  ]
  ```
  Sidechatters filenames are not hashed, so do not mark immutable unless renamed with a content hash (task 5).
- Update strategy: SW checks for update on load and on `visibilitychange` (throttled 1 h). `clientsClaim` off. Version stamp shown in Settings. Escape hatch: if a dynamic-import chunk 404s (old shell after deploy), catch `vite:preloadError` and `location.reload()` once.
- Preload: preload CSS-referenced bold font only if used above the fold; otherwise add `font-display: swap` to all three `@font-face` (check `index.css` lines 4-26 already have it for each; the Bold block was not confirmed).

## 3. (b) Data cache design

One small module, `client/src/lib/cache/` (no new dependency; React Query is an option but would be a larger refactor than this app needs):

```
cache/store.ts      // get/set/del over Mem + LS (+ IDB for big blobs), versioned envelope
cache/swr.ts        // readThrough(key, fetcher, {fresh, max, scope}) -> {data, stale, promise}
cache/keys.ts       // key builders: global("members"), user(uid,"profile"), ballot(uid,id,"detail")
cache/dedup.ts      // in-flight promise map keyed by key (collapses duplicate calls)
cache/clear.ts      // clearUserCache(uid), clearAll(); wired to onAuthStateChange SIGNED_OUT
```

Envelope: `{ v: CACHE_VERSION, at: epochMs, uid?: string, data }` stored under `jsc.cache.v1.<scope>.<key>`. Rules:

- **Versioning:** bump `CACHE_VERSION` on any change to the shape of a cached payload (types.ts / `Ballot`, `Category`, `Season`). On read, a mismatched `v` is discarded, never migrated. Also include the app build id so a deploy with schema change drops caches (simple: use `v` constant, bump by hand in the same PR as the type change; add a unit test that fails if `JSON.stringify` of a fixture's keys differs from a snapshot).
- **Per-user keys:** anything derived from RLS-filtered reads (profile, ballot summaries with `my_vote_count`, ballot detail visible to this user, my votes) is scoped by `uid`. Global scope only for data every signed-in member can see and that has no user-specific field: members, avatars map, season (without user fields).
- **Clear on log out:** `onAuthStateChange` event `SIGNED_OUT` (and user id change on `SIGNED_IN`) calls `clearUserCache(prevUid)` plus clears Mem. Also call it directly before `supabase.auth.signOut()` in AppShell, ProfilePage, ClaimNamePage (3 call sites). Keep the pending-vote journal (section 5) **until confirmed**: sign-out with unsent votes should warn, not silently drop.
- **Quota/failure:** every LS access in try/catch (pattern already used in `submission.ts`); if storage throws, fall back to Mem only. Cap LS use (~500 KB total); evict oldest by `at`.
- **SWR semantics:** `fresh` window returns cache without a request; between `fresh` and `max` returns cache and revalidates; past `max` or no entry waits for network. Revalidation results replace state; UI must not flash (compare JSON before setState).
- **Dedup:** the in-flight map returns the same promise for concurrent identical keys; this alone removes the 3x `fetchMembers` and the double `fetchBallotDetail` on Home.

### Must NEVER be cached, or must always be fresh

1. **Casting or clearing a vote** (`castVote`, `clearVote`): writes always go to the network (journal-first, see 5). Never "succeed" locally.
2. **Whether a vote is allowed** (ballot open/close): enforced by RLS on the server. Client uses fresh server `status/opens_at/closes_at` when within the window edges (+/- 10 min of `opens_at`/`closes_at`) and for the whole VotePage session: bypass cache, fetch on mount and on focus (already `useRefetchOnFocus`). Cached ballot state only used for first paint, and the vote buttons stay disabled (skeleton state) until the fresh fetch lands, unless offline (see 5). Use server clock skew: do not trust device clock beyond display; existing `classifySaveError` already re-fetches on rule denial, keep that.
3. **Results gate / release** (`seasons.results_released_at`, ballot `released` status): never use a cached value to decide to show results. Cached "not released" must revalidate on every Home mount (it is one tiny query); cached "released" is safe to keep (release is one-way) but results rows themselves are stored only after a fresh response confirmed the gate. Never store results payload pre-release. On `releaseSeasonResults` (committee) invalidate `season`, `ballots`, `results` for all keys.
4. **Committee flags** (`profiles.is_committee`) and committee-only data (`fetchAllVotes`, release status, tally, completion): not persisted. `RequireCommittee` must wait for a fresh profile read (or a read no older than the current session) before rendering committee routes or actions; a cached `true` may render skeleton chrome only. Real enforcement is RLS, but a stale flag after demotion must not expose UI.
5. **Auth/session**: no copy outside supabase-js. Never cache `getUser()` results across sign-in changes. Do not cache `member_name_status` / `available_member_names` (signup/claim race: a name claimed by someone else must appear taken; `resetMemberClaim` already guards with `expectedUserId`).
6. **Draft ballots and builder state** (committee): always fresh; saving rewrites categories (delete+insert), so ids change: cached ids would be wrong.
7. **Other members' votes / tallies before release.**
8. **Count queries used for deletion safety** (`countVotesBy`): fresh.

## 5. (d) Batching, dedup, first-paint skeletons

Query inventory for a member on Home today (released=false, ballots present): season (1), ballots (1), `auth.getUser` (1 network), categories (1), round_nominees (1), votes (1), plus `UserDataProvider` profile (1) + member (1), HomePage `profiles.image_url` (1). That is about 9 requests before paint, serial in two waves. Released adds members x3, profiles, ballot detail x N, results. Committee adds release status + all votes + members.

Optimizations (in order of payoff, lowest risk first):

1. Dedup in-flight + SWR for `fetchMembers` (3 calls become 1) and `fetchBallotDetail` per id (2 calls become 1).
2. Replace `auth.getUser()` with `auth.getSession()` (`session.user.id`, local, no round trip) in `fetchBallotSummaries`, `fetchMyVotes`, `castVote`, `clearVote`. Server still enforces `voter_id default auth.uid()` and RLS. Saves one round trip per vote save and unblocks offline queuing. **[LIVE VOTING]** (castVote/clearVote path.)
3. Drop `HomePage`'s separate `profiles.image_url` query; use `profile.image_url` from `UserDataProvider` (already loaded). Select explicit columns in `UserContenxt` instead of `*`.
4. `fetchMemberAvatars` should not call `fetchMembers` itself: take members as an argument or make it one joined select (`members` with `profiles(image_url)` if an FK exists, or one `profiles` select reused with the cached members).
5. Collapse `fetchBallotSummaries` three follow-ups into one RPC or a view (`ballot_summaries()` returning category_count and my_vote_count). Needs a migration; optional later.
6. `fetchReleaseStatus` re-fetches every ballot detail; pass the already-loaded `fetchSeasonResults`/summaries or only fetch category ids (`categories.select("id, ballot_id")`), since it only needs ids.
7. Start the Home fetch before the profile/member lookup finishes (committee flag only affects the extra jobs): kick off season + ballots in parallel with `UserDataProvider`, and `await` the flag only for committee jobs.
8. Skeletons: Home widgets and VotePage replace "Loading..." with `SkeletonScreen`/`Skeleton` shaped like final content (avoid layout shift); with SWR cached data present, render cached content immediately with no skeleton and a subtle "Updating" state only if revalidation is slow (>800 ms). Ballots list, Results, Profile similarly. Respect `ReduceMotion` for the shimmer.
9. Prefetch: on Home idle, prefetch the current open ballot's detail (`requestIdleCallback`) so tapping "Vote" paints instantly. Prefetch is a read into the same cache, so it falls under the same rules (VotePage still revalidates).

## 6. (e) Offline voting without lost or duplicate votes **[LIVE VOTING]**

Current queue: in-memory per-category promise chain, rollback to `confirmed` on failure, manual retry. Safe, but loses work on reload/close while offline.

Facts that make a durable queue safe:
- A vote is one row keyed (ballot_id, category_id, voter_id); `castVote` is an upsert; `clearVote` is a delete by that key. Replaying either any number of times converges to the same state. Duplicates are impossible; the only risks are (1) **ordering** (older queued write replayed after a newer one) and (2) **stale replay after the window closes or after a different device voted** (RLS rejects closed-window writes, which is correct and must be surfaced, not hidden).

Design:
- Journal in LS (`jsc.votequeue.v1.<uid>`): `{ballotId, categoryId, nomineeId|null, seq, clientTs}` keyed by (ballotId, categoryId): **only the latest intent per category is kept** (coalesce). This enforces ordering by construction.
- On tap: UI shows pending (existing behavior), journal entry written *first*, then the network attempt. On success: remove entry (only if its `seq` equals the sent seq, so a newer tap is not erased). On network-class failure (`classifySaveError` offline / fetch failed): keep entry, show "Saved on this device, will send when online" (a distinct state, never "Voted"). On rule/closed denial: drop entry, show closed message (existing).
- Flush triggers: `online` event, `visibilitychange`, app start (after fresh ballot detail loads), and a manual "Send now". Flush uses the same `castVote`/`clearVote`, sequentially per category.
- Before flushing, re-fetch ballot detail and `fetchMyVotes` fresh; if the window is closed, discard with a visible "These votes arrived after the ballot closed and were not counted" notice. Never retry rule denials in a loop.
- Do not apply server-vs-local "merge" silently: if the server has a different value than `confirmed` (cast on another device) and a journal entry exists, the later user intent (journal) wins, which is what upsert does anyway; show a toast listing overwritten categories.
- Submission confirmation (`jsc.submitted...`) must be blocked while journal entries exist for that ballot (otherwise "submitted" can lie). Sign-out with pending entries: confirm dialog.
- Offline display of the ballot itself requires cached ballot detail (item 12); allow *viewing and queueing* offline against the cached detail, but flag that the window may have closed ("Will count only if the ballot is still open when sent").
- Background Sync API is not on iOS Safari: do not depend on it; use foreground triggers only.
- Do not move this into the service worker: keep the logic in the page where tests exist (`VotePage.test.tsx`, `voting.test.ts`).

Test matrix (must exist before merging): tap twice quickly offline then online (one write, last value); tap A, go offline, tap B, reload, online (B sent once); clear while offline then online; close mid-queue then flush after close (discarded + notice); two tabs (same journal: use `storage` event or a tab lock via `navigator.locks`, or only flush from the visible tab); sign-out/in as another user (journal not leaked: per-uid key); storage full (falls back to in-memory chain, current behavior).
